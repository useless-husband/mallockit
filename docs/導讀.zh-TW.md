# mallockit 導讀（給第一次接觸記憶體配置器的人）

這份導讀用白話解釋這個專案在做什麼、幾個關鍵觀念、哪個檔案負責什麼，最後附上 10 個面試可能會被問到的問題和簡短答案。看完應該能自己向面試官講清楚這個專案。

## 一句話說明

自己從零用 C 寫一個 `malloc`／`free`（程式要記憶體、還記憶體時呼叫的那兩個函式），照 MIT 6.172「軟體效能工程」第 3 個專案（動態記憶體配置器，用「空間利用率」和「速度」打分數）的精神出發，再一路做到可以讓真的程式（DuckDB、SQLite、Python、Lua）改用它來跑，並且和 macOS 內建的 malloc、微軟的 mimalloc、Facebook 用的 jemalloc 實際比賽。設計主要參考 mimalloc，是學習用的重做，不是新的發明。

## 先搞懂：malloc 到底在做什麼？——倉庫和置物櫃

把電腦記憶體想成一間**大倉庫**，作業系統是倉庫管理員，但他只肯「整區整區」出租（一次最少 16 KB，在 Apple M 晶片上），而且每次去找他都要排隊填表（這叫**系統呼叫**，很慢，大約是普通函式呼叫的幾百倍）。

程式卻常常只要很小一格：存一個名字 20 個位元組、一個節點 48 個位元組。所以中間需要一個**置物櫃管理員**，就是 `malloc`：

1. 先向倉庫一次租一大區（mallockit 一次租 4 MB，叫做一個 **segment**）。
2. 把大區切成很多排**置物櫃**，每一排的格子都一樣大（同一排叫一個 **page**，同一種格子大小叫一個 **size class**）。
3. 有人要 20 個位元組，就給他「32 位元組那一排」裡的一格；用完（`free`）就把格子收回來，下次給別人。

難的地方是：要**快**（很多程式每秒呼叫幾千萬次）、**省空間**、而且**很多人（執行緒）同時來借還**也不能出錯。

## 7 個關鍵觀念，每個配一個生活比喻

### 1. Size class（格子大小分級）：衣服只做 S/M/L

如果每個人要多大就切多大，收回來的格子大小參差不齊，很難再利用。所以只做固定幾種尺寸：128 位元組以下每 16 位元組一級，再大就每「翻倍」分 4 級（160、192、224、256、320……）。要 130 位元組就給 160 的格子，浪費最多不到 20%。這叫**內部碎片**（格子比你要的大，多出來的空間別人也不能用）。

### 2. 碎片（fragmentation）：停車場的零碎空位

停車場有 10 個空位，但都是零散的單格，來了一台需要連續 3 格的巴士就停不下。記憶體也一樣，**外部碎片**是「總空間夠，但被切得太零碎」。mallockit 的做法：同一排置物櫃只放同一種大小，一整排都空了就整排還給倉庫，換成別的大小用，所以不會出現大小混雜的零碎空間。代價是：一排裡只要還有一格在用，整排就不能還。

### 3. 每個執行緒有自己的櫃台：為什麼比一把大鎖快

最簡單的做法是整間置物櫃只有一個櫃台，大家排隊（一把**全域鎖**）。10 個執行緒同時來就只能一個一個處理。mallockit 讓**每個執行緒有自己的一套置物櫃**（叫 **heap**），借和還自己的東西都不用排隊、不用上鎖。實測 larson 這個多執行緒伺服器模擬測試，macOS 內建 malloc 每秒約 1500 萬次操作，mallockit 約 2 億次。

### 4. 別人來還東西：門口的投遞箱

A 執行緒借的格子，可能被 B 執行緒還回來（例如一個執行緒負責生產資料、另一個負責處理完丟掉）。B 不能直接動 A 的櫃台（會撞在一起），所以每一排置物櫃門口有一個**投遞箱**（`xthread_free`），B 只要用一個**原子操作（CAS）**把格子丟進去；A 自己的格子用完時，再一次把投遞箱整箱倒回來。這叫 **free list sharding**：每一排有三條清單——可以借出的、自己還的、別人還的。

### 5. 執行緒結束了怎麼辦：店長離職，新店長接手

執行緒結束時，它的置物櫃裡可能還有東西被別人借著。mallockit 不會把它丟掉，而是把整套置物櫃標成「沒有店長」（**abandon**），之後新開的執行緒直接**整套接手**（**adopt**）。測試顯示，如果不這樣做，某些測試的記憶體會從幾十 MB 暴增到幾 GB。

### 6. False sharing（偽共享）：兩個人共用一本筆記本

CPU 讀寫記憶體不是一個位元組一個位元組，而是一次一整「行」（cache line，M 晶片上是 128 位元組）。如果兩個執行緒各自改自己的變數，但兩個變數剛好在同一行，CPU 就得把這行在兩個核心之間搬來搬去，好像兩個人輪流搶同一本筆記本寫字。配置器如果把兩個執行緒的小物件放在同一行，就會害程式變慢。mallockit 每個執行緒有自己的 page，所以不同執行緒拿到的小物件不會擠在同一行（`cache-scratch` 測試專門量這件事）。

### 7. 還給作業系統：退租要挑時機

整排空了要不要馬上還給倉庫？馬上還，記憶體用量低，但如果程式下一秒又要，就要重新租、重新清潔（page fault），很慢。mallockit 的策略：空了的頁等 10 毫秒還沒人用才還（`madvise`），空的 4 MB 區先放在一個小倉（cache）裡，但最多只留 64 MB 沒還的。這是「省記憶體」和「快」之間的取捨，在 malloc-large 測試裡 mallockit 用的記憶體比系統少，但速度比較慢，報告裡有寫。

## 數據會騙人：量測時要注意的事

- **機器在忙別的事**：這台電腦同時有其他工作在跑，同一個測試跑兩次可能差 30%。所以每個測試重複 3～5 次、取**中位數**，並記錄最小和最大值，各配置器**輪流交錯**執行（不是先跑完 A 再跑 B），避免某一個剛好碰上電腦很忙。
- **大核和小核**：M5 有 4 個效能核心（P）和 6 個節能核心（E）。執行緒超過 4 個時，有些會跑到比較慢的 E 核心上，所以曲線在 4 的地方會彎；在 E 核心上跑同一個單執行緒測試會慢好幾倍。
- **「記憶體用量」要量對**：macOS 上 `ru_maxrss`（常駐記憶體）會把配置器已經「還回去、但系統還沒收走」的頁也算進去，所以這個專案在 macOS 用的是「physical footprint」（活動監視器顯示的那個數字）。一開始我沒注意這點，誤以為某個設計很浪費記憶體。
- **公不公平**：所有配置器跑的是同一支程式（同一個執行檔），只是用環境變數換掉 malloc；jemalloc 在 macOS 上預設走「zone」的方式，每次呼叫多一層轉接，這對它不利，報告裡有註明。

## 檔案導覽：哪個檔案做什麼

| 檔案 | 做什麼 |
|---|---|
| `include/mallockit.h` | 對外的函式：`mk_malloc`、`mk_free`、`mk_realloc`、統計、回收 |
| `src/os.c` | 跟作業系統要記憶體（`mmap`）、還記憶體（`munmap`、`madvise`）、查頁大小 |
| `src/segment.c` | 4 MB 的 segment、分頁、空 segment 的小倉（cache）、大物件 |
| `src/page.c` | 一排置物櫃的三條清單：切新格子、把投遞箱倒回來、滿了的頁 |
| `src/heap.c` | 每個執行緒的 heap、執行緒結束時交接、`fork` |
| `src/alloc.c` | `malloc`／`free` 的快速路徑（最常走的那幾行）和其他 API |
| `src/debug.c` | 除錯版：抓寫超過、重複 free、free 錯指標、free 後還在寫 |
| `src/override.c` | 讓整個程式改用 mallockit：Linux 用 `LD_PRELOAD`，macOS 用 malloc zone + dyld interpose |
| `tests/` | 每一層的單元測試、隨機操作測試、多執行緒壓力測試、除錯模式測試 |
| `bench/` | 比賽用的腳本：抓 mimalloc/jemalloc、跑 mimalloc-bench 的測試、6.172 風格分數 |
| `tools/` | 突變測試（故意放 bug 看測試抓不抓得到）、消融實驗、真實程式測試 |
| `docs/results.html` | 量測結果網頁；`docs/report.md` 是像課程報告的完整說明 |

## 怎麼證明它是對的

1. **單元測試**：每一層各自測（size class、作業系統層、segment、page、heap、API）。
2. **隨機操作測試**：用固定亂數種子產生幾十萬次 malloc/realloc/free，每塊記憶體填上特定圖案，檢查有沒有重疊、對齊對不對、realloc 有沒有弄丟資料。失敗時會印出種子，可以重現。
3. **多執行緒壓力測試**：生產者/消費者、隨機交換、執行緒一直生生死死；最後檢查記憶體有沒有全部回來。
4. **ThreadSanitizer**：專門抓「兩個執行緒同時改同一個變數」的工具，全部測試在它底下跑過。
5. **除錯模式**：每個抓錯功能都有一個「故意做錯」的測試。
6. **突變測試**：故意在程式裡放一行 bug（例如 size class 算小一格、跨執行緒 free 忘了用原子操作），確認測試會失敗。
7. **真實程式**：DuckDB 查詢、SQLite、C 編譯器編譯 SQLite 原始碼、Lua 官方測試、CPython 的測試，結果都要和系統 malloc 一模一樣。

## 10 個面試可能會問的問題

**Q1. malloc 為什麼不直接每次跟作業系統要記憶體？**
系統呼叫很慢（微秒等級），而且作業系統最小單位是一頁（16 KB）。malloc 一次要一大塊，自己切小格分給程式，大部分呼叫只要幾奈秒。

**Q2. 內部碎片和外部碎片差在哪？**
內部碎片：給的格子比要的大（要 130 給 160，多的 30 浪費）。外部碎片：空閒空間總和夠，但被切得太零碎，湊不出要的大小。mallockit 用 size class 把內部碎片限制在 20% 內，用「同一頁同一大小、整頁空了才換用途」避免外部碎片。

**Q3. free 只拿到一個指標，怎麼知道這塊多大、屬於誰？**
每個 4 MB segment 都對齊在 4 MB 的邊界，所以把指標的低 22 位元清掉就是 segment 的開頭，那裡存著每一頁的資訊（格子大小、擁有者）。不需要在每塊記憶體前面放標頭，也不用查表。

**Q4. 多執行緒時為什麼不加一把鎖就好？**
正確但慢：所有執行緒排隊。mallockit 每個執行緒有自己的 heap，自己借還完全不用鎖；別的執行緒還東西用一個 CAS 丟進投遞箱。larson 測試裡比系統 malloc 快十倍以上。

**Q5. CAS 是什麼？為什麼「別人還的」要用它？**
Compare-And-Swap：「如果這個位置現在還是 X，就把它改成 Y」，整個動作不會被打斷。兩個執行緒同時往同一個投遞箱丟東西時，用普通的讀和寫會有一個人的東西被蓋掉（遺失）。突變測試就是把它改成普通讀寫，壓力測試立刻抓到有記憶體回不來，ThreadSanitizer 也直接報 data race。

**Q6. 什麼是 false sharing？配置器怎麼影響它？**
兩個核心改同一個 cache line 裡的不同變數，那一行會在核心之間來回搬，變很慢。如果配置器把不同執行緒的小物件放在同一行，程式本身沒錯也會變慢。mallockit 每個執行緒從自己的頁拿格子，所以不會。

**Q7. 執行緒結束了，它借出去的東西怎麼辦？**
它的 heap 被標成無主（abandoned），之後別的執行緒還東西照樣用投遞箱；新開的執行緒會整套接手（adopt）。沒有新執行緒時，其他執行緒在需要新記憶體前會順手幫忙整理無主的 heap，把空的頁還回去。

**Q8. 你怎麼確定 benchmark 數字可信？**
同一支執行檔、只換 malloc；每項重複 3～5 次取中位數並列出範圍；各配置器輪流交錯跑；記錄當時的系統負載；記憶體用 physical footprint；輸了的項目（xmalloc-test、malloc-large）也照實寫出來並分析原因。

**Q9. 你的配置器輸在哪裡？為什麼？**
malloc-large（反覆配置 5～25 MB 的大區塊）：我們為了省記憶體，最多只留 64 MB 沒還的空間，所以常常要 `madvise` 還回去再要回來，比系統慢約一倍但記憶體少約三成。xmalloc-test（一個執行緒專門配置、另一個專門釋放）：mimalloc 快 1.2～1.7 倍，我量過並排除了「頁描述子的 false sharing」這個猜測，真正原因還沒找到。mstress 在 6 個執行緒以上也輸 mimalloc（最多慢 1.4 倍），這個測試每一輪都把執行緒全部結束再重開，heap 交接的成本比較明顯。整體來說：比系統 malloc 快約 2 倍、比 jemalloc 快約 1.8 倍、是 mimalloc 的 0.93 倍。

**Q10. 如果要繼續改進，你會做什麼？**
(1) 64 KB～4 MB 的物件改成在 segment 裡切多頁（像 mimalloc v2 的 span），不要一個物件佔一整個 segment；(2) 執行緒閒置時用計時器幫它還記憶體；(3) Linux 上大物件 realloc 改用 `mremap`，不用複製；(4) 把 xmalloc-test 的差距用硬體效能計數器查清楚。
